# Arch Linux Terminal VPN Client (archvpn) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a blazing-fast, beautiful terminal VPN client for Arch Linux (`archvpn`) powered by `sing-box` in TUN mode, supporting VLESS/Reality/Vision subscriptions with concurrent latency benchmarking and an interactive Charm Bubbletea TUI + CLI mode.

**Architecture:** A standalone Go application (`archvpn`) manages subscriptions, fetches and decodes base64 VLESS/Reality/Vision nodes, performs concurrent TCP/TLS ping tests, dynamically compiles optimal `sing-box` TUN configurations, and supervises the `sing-box` background process with automatic DNS and route cleanup on exit. It exposes both an interactive Bubbletea/Lipgloss TUI and scriptable CLI subcommands (`connect`, `disconnect`, `status`, `update`, `ping`) suitable for Waybar/Hyprland integration.

**Tech Stack:** Go (1.27+), Charm Bubbletea (`github.com/charmbracelet/bubbletea`), Lipgloss, `sing-box` (v1.14+ in Arch Linux `extra`), Linux TUN interface, `notify-send`.

**Spec:** In-chat approved architecture based on user's 3 VLESS/Reality subscription links, system-wide TUN routing, and Arch Linux terminal experience.

## Global Constraints
- Target platform: Arch Linux x86_64 with Linux kernel TUN device support (`/dev/net/tun`).
- Backend core: `sing-box` (installed via Arch Linux official repository).
- Subscriptions: Handles Base64-encoded lines of `vless://` URLs with Reality, Vision, XHTTP, gRPC, and standard TLS transports.
- No network leakage or DNS hang on sudden exit/SIGINT/SIGTERM (trap signals to gracefully shut down `sing-box` and restore system resolv.conf/routing).
- Config and data directory strictly in `~/.config/archvpn/`.

## Review Focus
- **Malformed or unreachable subscription links:** Subscription parser must skip invalid lines, report errors non-fatally, and preserve existing working nodes in the cache.
- **Port or TUN conflicts:** Verify port availability and clean up existing orphaned `sing-box` instances before launching a new tunnel.
- **Root / sudo privileges for TUN interface:** Gracefully check for elevated privileges needed for TUN device creation, or configure `setcap cap_net_admin,cap_net_bind_service=+ep /usr/bin/sing-box` so the client can run seamlessly.
- **DNS leak prevention:** sing-box TUN configuration must configure robust DNS servers (`1.1.1.1`, `8.8.8.8`) with direct routing for the VPN server IP itself to prevent recursive routing loops.
- **Signal handling:** SIGINT / SIGTERM / Ctrl+C in TUI or CLI must immediately terminate the child `sing-box` process to prevent orphaned network lockouts.
